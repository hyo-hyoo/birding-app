# 观鸟 Web App｜项目概览与暂定技术路线

> 文档状态：持续维护  
> 本文档只记录长期相对稳定的项目方向。

## 1. 项目定位

开发一个面向普通观鸟用户、以手机浏览器使用为主的移动端优先 Web App。

项目来源于真实观鸟体验：用户外出观鸟时主要使用望远镜，没有拍到照片，或不希望依赖照片识别。观察对象可能距离较远，停留时间较短；如果无法当场确认鸟种，颜色分布、局部花纹和其他细节容易在回家前逐渐遗忘。

产品希望帮助用户把短暂、模糊但有价值的观察印象保存下来，以便之后继续查找、比较、修改和确认，而不是简单复制现有的照片识鸟或声音识鸟产品。

第一版应当规模可控，并形成一个可以实际运行、演示、测试和说明的完整闭环。

## 2. 当前产品核心方向

当前产品主线已经聚焦为：

> 通过结构化方式记录鸟的整体轮廓、身体不同部位的颜色、花纹和观察者的确定程度，并据此生成一张抽象鸟类印象图和文字特征摘要。

抽象鸟类印象图用于外化观察者当时脑中的视觉印象，帮助之后回忆和继续辨认。它不追求照片级真实，也不宣称客观还原观察对象。

第一阶段的核心价值是保存一次尚未完成的辨认过程，而不是自动给出准确鸟种答案。

## 3. 核心用户与使用场景

核心用户包括：

- 外出观鸟时主要使用望远镜的普通观鸟者；
- 没有拍到照片，或不希望依赖照片识别的用户；
- 观察时间较短、无法当场确认鸟种的用户；
- 希望在记忆消退前保存视觉印象，并在之后继续查找和确认的用户。

第一阶段优先考虑福冈日常可能遇到的观鸟场景，以停在树枝、地面活动或水边活动的鸟为主。飞行中的鸟暂时不是主要设计对象。

## 4. 当前产品形态

### 第一阶段

- 面向普通用户的 Web App；
- Mobile-first，优先保证手机浏览器体验；
- 以个人观察记录及其后续查看、修改和确认为核心；
- 暂时不以管理员后台作为主要产品形态；
- 暂时不开发原生 Android App；
- 暂时不开发原生 iOS App；
- 暂时不开发微信小程序；
- 暂时不依赖 LINE MINI App 才能运行。

### 后续可能扩展

项目成熟后，可以再评估：

- PWA；
- 用于个人测试、暂不公开发布的 LINE MINI App；
- Rails API；
- 如果未来确实希望将产品落地，购买 MacBook 后评估原生 iOS 开发。

以上内容不属于当前 MVP 的完成条件。

## 6. 前端方向

前端用于承载面向用户的移动端体验，但不是本项目最主要的学习方向。

第一阶段优先考虑：

- HTML；
- CSS；
- JavaScript；
- Rails Views；
- 必要的 ERB 模板语法；
- Turbo；
- Stimulus；
- 少量普通 JavaScript。

抽象鸟类印象图采用服务器生成的 inline SVG；预览按普通 Rails 提交、Turbo Frame 局部替换和 Stimulus 自动触发的顺序渐进实现。数据库只保存结构化观察数据，不持久化生成后的 SVG 或文字摘要。

MVP 不采用：

- 完整 React 前端；
- Vue；
- 完整 React 或 Vue SPA；
- 独立前端仓库；
- 仅提供 JSON API 的后端。

前端设计、CSS 和响应式适配可以大量由 AI 辅助，但开发者需要理解完整数据流：

用户操作  
→ JavaScript 或表单事件  
→ Rails Routing  
→ Controller  
→ Model 与数据库  
→ 返回页面或数据  
→ 前端更新显示

## 7. Ruby 与 Rails 的学习方式

- `select`；

## 8. 与 Java 经验的连接

用户有 Java 和 Java Web 开发经验，但没有 Ruby 和 Rails 经验。

学习 Ruby 和 Rails 时，需要持续与 Java 进行对比，帮助理解不同语言和框架解决相同问题时的设计差异。

重点比较：

- 静态类型与动态类型；
- Java Class 与 Ruby Class；
- `null` 与 `nil`；
- Java Stream 与 Ruby 的 `map`、`select`；
- Spring MVC 与 Rails MVC；
- JPA/Hibernate 与 Active Record；
- Repository/DAO 与 Rails Model 查询；
- Maven/Gradle 与 Bundler/Gemfile；
- Java 注解与 Rails 约定及 DSL；
- Java 分层结构与 Rails 职责划分。

比较的目的不是简单判断哪一种语言或框架更好，而是：

- 迁移已有知识；
- 理解设计思想；
- 识别 Rails 的便利与风险；
- 形成可以在转岗面谈中说明的真实学习过程。

## 9. AI 使用原则

不采用把全部需求一次性交给 AI、直接生成整个项目的方式。

开发过程中遵守以下原则：

1. 每次只实现一个范围清楚的小任务。
2. 先让 AI 解释实现方案和技术取舍，再生成或修改代码。
3. 必须理解修改了哪些文件，以及数据如何流动。
4. 每完成一个独立功能就进行 Git 提交。
5. AI 完成代码后，还需要运行、测试和审查。
6. 对自己无法解释的关键代码，不直接视为完成成果。
7. AI 主要承担解释、提出方案、生成初稿和代码审查。
8. 技术选择、范围控制和最终验证由开发者自己完成。
9. 不为了展示 AI 能力而扩大功能范围。
10. 不为了避免错误而无限研究 AI 工作流后才开始项目。

## 11. Figma 与 UI 设计流程

Figma 用于整理用户流程和界面设计，不作为项目资料的唯一保存位置。

建议流程：

1. 先绘制低保真页面流程。
2. 确定 MVP 包含的页面。
3. 选择一个核心页面制作视觉基准。
4. 确定字体、间距、按钮、卡片和色彩规则。
5. 页面流程进一步明确后，再创建并维护 `ui-design.md`。
6. 在文档中保存 Figma 文件链接。
7. 使用 Figma 截图、设计说明和链接辅助 Codex 实现。
8. 在桌面浏览器和手机浏览器中检查实际效果。
9. 根据真实使用效果继续调整设计与代码。

第一阶段不要求掌握专业 UI 设计技能，也不要求所有页面设计完成后才开始开发。
